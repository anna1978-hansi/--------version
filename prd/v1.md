# 项目 PRD v1

## 1. 项目概述

本项目是一个个人使用的“面试录音复盘系统”。

核心目标：

1. 输入一份面试录音转写文本。
2. 调用 LLM 将原始文本整理为“按轮次拆分”的问答结构。
3. 将轮次结果存入本地 SQLite。
4. 前端以目录 + 详情页的方式展示每一轮问答。
5. 允许用户对 AI 识别错误的轮次进行人工修正。

当前系统定位：

- 不是追求 100% 自动识别。
- 目标是“80% 自动正确 + 20% 人工修正”。
- 人工修正优先支持：
  - 合并两轮
  - 删除一轮

## 2. 当前技术架构

### 2.1 目录结构

- `deepseek-test.js`
  - 调用 DeepSeek 接口
  - 生成 prompt
  - 获取 LLM 结果
  - 产出 `reply.txt`、`response.json`、`turns.json`
  - 调用数据层写入 SQLite

- `backend/interview-store.js`
  - SQLite 数据层
  - 负责解析、存储、查询、merge/delete

- `backend-server.js`
  - Node HTTP 服务
  - 提供 REST API

- `frontend/`
  - React + TypeScript + Vite 前端
  - 当前为单页复盘工作台

- `scripts/import-interview.js`
  - 将已有 AI 回复重新导入数据库

### 2.2 技术栈

- 后端：
  - Node.js
  - `node:sqlite` / `DatabaseSync`
  - 原生 `http`

- 前端：
  - React 18
  - TypeScript
  - Vite

- 数据库：
  - SQLite

## 3. 核心业务流程

### 3.1 数据流

1. 原始文本文件输入：
   - 示例：`标准录音 6.mp3.txt`

2. `deepseek-test.js` 读取原始文本并构造 prompt。

3. 调用 DeepSeek `/chat/completions` 接口，要求输出格式：

   - `第1轮`
   - `面试官：...`
   - `面试者：...`

4. 模型回复保存到：
   - `output/deepseek-test.reply.txt`
   - `output/deepseek-test.response.json`

5. 后端使用 `parseInterviewTurns(rawReply)` 解析原始轮次。

6. 后端使用 `normalizeInterviewTurns(turns)` 对明显错拆做展示层归一化。

7. 数据写入 SQLite：
   - `interview_sessions`
   - `interview_turns`
   - `interview_messages`

8. 前端请求 `/api/sessions/:sessionKey/turns` 获取当前可展示轮次。

9. 用户如果发现轮次不对，可在前端进入“整理目录”模式，进行：
   - merge
   - delete

10. 前端确认后调用后端接口，后端直接修改原数据库，再返回最新结果。

## 4. 数据库设计

### 4.1 `interview_sessions`

会话级信息。

主要字段：

- `session_key`
- `title`
- `source_file_path`
- `reply_file_path`
- `model`
- `total_rounds`
- `created_at`
- `updated_at`

### 4.2 `interview_turns`

原始存储的轮次表。

主要字段：

- `id`
- `session_key`
- `round_number`
- `interviewer_text`
- `interviewer_needs_review`
- `candidate_text`
- `candidate_needs_review`
- `raw_block`
- `created_at`
- `updated_at`

说明：

- 这里存的是数据库当前“真实状态”。
- merge/delete 会直接改这个表。
- 当前版本不保留历史修订记录。

### 4.3 `interview_messages`

按轮次拆成消息级别的表。

主要字段：

- `id`
- `session_key`
- `turn_id`
- `round_number`
- `role`
- `speaker_label`
- `content`
- `needs_review`
- `sequence_in_round`
- `created_at`

说明：

- 每轮通常最多两条消息：
  - `interviewer`
  - `candidate`
- merge/delete 后需要同步重建或删除这张表对应记录。

## 5. 轮次归一化策略

### 5.1 当前策略

后端存在一层 `normalizeInterviewTurns(turns)`，用于修正一些“明显错误拆轮”。

典型场景：

1. 问题被拆到了上一轮的“面试者”字段里，回答被拆到了下一轮的“面试官”字段里。
2. “好的 / 嗯”这种承接词被单独拆成一轮。
3. 一个提问被错误切成两轮。

### 5.2 当前限制

这层规则不是万能的。

结论：

- 自动化只能覆盖明显模式。
- 剩余问题需要人工校验。
- 因此系统新增了人工 merge/delete。

### `GET /api/sessions/:sessionKey`

## 6.4 获取当前展示轮次

### `GET /api/sessions/:sessionKey/turns`

说明：

- 返回的是“当前可展示轮次”。
- 已经过归一化。
- merge/delete 之后，这个接口也返回更新后的数据。

返回：

    "model": "deepseek-chat",
    "totalRounds": 33,
    "createdAt": "2026-03-22T08:01:08.437Z",
    "updatedAt": "2026-03-22T08:04:52.518Z"
  },
  "items": [
    {
      "roundNumber": 9,
      "sourceRoundNumbers": [9, 10],
      "normalizationNote": "merged_split_qa_pair",

查询参数支持：

- `fromRound`
- `toRound`
- `limit`
- `offset`

## 6.5 获取消息级数据

### `GET /api/sessions/:sessionKey/messages`

返回消息级视图。

当前前端主页面未强依赖这个接口，但数据库层已支持。

## 6.6 导入会话

### `POST /api/sessions/import`

请求体：

```json
{
  "sessionKey": "optional",
  "title": "标准录音 6",
  "sourceFilePath": "/abs/path/source.txt",
  "replyFilePath": "/abs/path/reply.txt",
  "rawReply": "第1轮 ...",
  "model": "deepseek-chat"
}
```

## 6.7 合并轮次

### `POST /api/sessions/:sessionKey/turns/merge`

用途：

- 前端人工确认后的智能合并。
- 当前只支持合并“展示层中相邻的两轮”。

请求体：

```json
{
  "roundNumbers": [9, 10],
  "mergedInterviewerText": "好的，这边比较熟悉 HTTP 和 HTTPS，可以讲一下它们都有哪些核心差异吗？",
  "mergedCandidateText": "因为我觉得 HTTPS 最主要的是..."
}
```

后端行为：

1. 校验只传了两个轮次。
2. 校验这两个轮次在展示层中相邻。
3. 找到它们对应的来源轮次。
4. 直接修改数据库中的原始轮次表。
5. 保留第一组来源轮次中的第一条 turn。
6. 删除其他来源 turn。
7. 重建对应 `interview_messages`。
8. 返回最新 `/turns` 结果。

返回：

```json
{
  "ok": true,
  "session": { "...": "..." },
  "items": [ "...最新轮次列表..." ]
}
```

## 6.8 删除轮次

### `POST /api/sessions/:sessionKey/turns/delete`

用途：

- 删除当前展示中的一轮。

请求体：

```json
{
  "roundNumber": 10
}
```

后端行为：

1. 找到该展示轮次对应的来源轮次。
2. 直接删除原始 turn 和对应 messages。
3. 更新 session 的 `total_rounds`。
4. 返回最新 `/turns` 结果。

## 7. 前端页面设计

## 7.1 当前页面结构

页面为三栏布局：

1. 左侧目录区
   - 显示轮次列表
   - 可进入编辑模式

2. 中间详情区
   - 展示当前轮次的面试官内容
   - 展示当前轮次的面试者内容

3. 右侧辅助区
   - AI 诊断
   - 继续深挖

## 7.2 目录编辑模式

左侧目录支持“整理目录”模式。

交互：

1. 点击“整理目录”进入编辑态。
2. 用户可点选目录项。
3. 选中 1 项：
   - 允许删除
4. 选中 2 项且相邻：
   - 允许合并

## 7.3 合并弹窗

当前版本为人工确认式 merge。

弹窗内容：

1. 展示两轮的当前内容：
   - 当前面试官内容
   - 当前面试者内容

2. 每个内容块都可点击：
   - 加入面试官
   - 加入面试者

3. 下方提供两个最终编辑框：
   - 合并后的面试官内容
   - 合并后的面试者内容

4. 用户确认后调用后端 merge 接口。

设计原则：

- 不再依赖 LLM 二次改写。
- 最终内容由用户确认。
- 后端只负责写库，不负责替用户做语义判断。

## 7.4 删除确认

删除使用浏览器确认框：

- 用户确认后调用 delete 接口
- 成功后重新拉取 `/turns`

## 8. 前后端对接方式

### 8.1 前端数据拉取顺序

1. 页面初始化调用 `GET /api/sessions`
2. 取第一条 session
3. 调用 `GET /api/sessions/:sessionKey/turns`
4. 渲染目录和详情

### 8.2 变更后的刷新逻辑

当前策略：

- merge/delete 成功后，不在前端本地硬拼状态。
- 直接重新请求 `/api/sessions/:sessionKey/turns`
- 用最新接口结果刷新页面

这样做的理由：

- 简单
- 状态一致性更高
- 不容易前后端错位

## 10. 当前约束与已知问题

1. LLM 角色判断仍然不可能 100% 正确。
2. 当前 merge/delete 是直接改原数据库，不保留历史版本。
3. 当前展示轮次号是“展示层顺排编号”，不是原始数据库 round number 的直接映射。
4. 当前 merge Modal 默认不自动填最终结果，主要依赖用户手工确认。
5. 当前 delete 只支持单轮删除。
6. 当前 merge 只支持两轮相邻合并。
7. 当前没有 undo / redo。

## 11. 推荐启动方式

项目根目录运行：

```bash
npm run backend
```

```bash
npm run frontend:dev
```

说明：

- `backend/interview-store.js` 不是服务入口。
- 正确服务入口是 `backend-server.js`。
- Node 的 SQLite 会打印 experimental warning，这是警告，不是启动失败。
