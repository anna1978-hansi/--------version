第1轮
面试者：然后我当初就很痛苦。然后它报错是说的，就是在一个代码上面提交的时候，报的是一个 store 的问题。就是你用了一个比如说 `cut` 这个变量，然后它就说你这个有一个 `undefined` 的问题。
面试者：就相当于是，问题的根源是说你这个 store 是找不到的。

第2轮
面试者：但是我看了一下，因为这个问题其实比较复杂。因为当初我们团队有人改过一个 E-Line。
面试者：然后他没有重新打过这个 E-Line 包，就把别人升级了。

第3轮
面试者：然后我当初就怀疑，是不是他更新 E-Line 出了问题。我就是先去检查了它的 E-Line 版本。
面试者：然后发现它 E-Line 版本升级了，我当初就怀疑是不是它更新依赖出了问题，我就是先去检查了它的依赖版本。

第4轮
面试者：然后发现，它依赖版本升级是正确的。
面试者：然后这个时候，因为它是别人的组件库嘛。

第5轮
面试者：然后就是，我开始的时候，就是说我这个项目打了一个新包，在别人组件库下面使用是 OK 的。
面试者：然后说明它的问题是热更新的问题。

第6轮
面试者：然后我想了一下，就是说去排查，因为那个是别人的组件，别人一个月内有很多 Git 的提交嘛。
面试者：然后我就回到了我上一次、就一个月前改了一次代码，然后就从这一次到他们最新的提交之间，看他们的 Git 记录，然后自己启动去看一下，到底是哪一次 Git 出了问题。

第7轮
面试者：然后这个问题，我找到了那个错误的 Git 提交之后，我就去看了一下它具体新增的代码那一块。
面试者：就确实是跟它那个报错是有关系的。

第8轮
面试者：但是它这个问题比较离谱。就是因为这个问题，我其实自己是没有 get 到的。
面试者：我就是把这个错误的代码交给 AI，然后 AI 知道了增量的错误代码之后，再去识别这个问题。

第9轮
面试者：它发现的问题是在于一个导入方式的影响。就是你简单理解为，这个时候它比如说是 `import` 一个 A，然后 `../../../src/A/B`。
面试者：然后或者是向上找两层，再 `/A/B` 的这种写法。

第10轮
面试者：然后就是，这个本身如果是普通前端的话，这种导入方式是 OK 的。
面试者：但是这个是在 RN 里面，因为 RN 它是一个 Metro 结构，然后它找包的时候，就把那个 `src` 路径，相当于是热启动的时候就找错了。

第11轮
面试者：然后就像是它认为它创建了一个全新的 store 实例。
面试者：然后就导致它跟它原先下面的 store 实例不一样，然后就冲突了。

第12轮
面试者：就这个问题，到时候我其实发现的时候，就很离谱。
